# 要件

何を・なぜ。手段は [ADR](adr/)。

## 問題・ユーザー

手作業: トレンド調査 / 重複確認 / 有用論文の発見 / **次のテーマ候補** / 参考文献の整理。

- 論文を書く研究者。未公開データ・原稿を手元に持つ
- 分野非依存。配布する（`C-02`）
- **特定の参考文献マネージャ（Zotero 等）への依存は前提にしない**

## 成功条件（初版）

1. アプリ未起動でも、**課題意識が近い候補**が日次でクラウドに溜まる（収集は Queue。時間をかけてよい）
2. 起動すると候補が手元に入り、**課題意識・関連技術との類似度で順位づけ**された一覧が読める（有効／除外は断定しない）
3. **ログイン済みなら、待ちきれずに自発で調査を開始できる**（Queue 投入。収集本体は cron と同じ経路）
4. 各候補に**要約（要旨）**があり、上から読んで本当に関連なら**ワンクリックでアプリ内参考文献へ**入れられる。入れた文献は OA 直リンクがあれば PDF をローカルに取る
5. 執筆中原稿の主張を検査できる
6. 外部 LLM を統制下で呼べる（**利用自体が目的**。ゲートウェイは ADR-0002）
7. 新着から次のテーマ候補を提示できる
8. **GUI と同じローカルデータに CLI から触れられる**

やらない: 全分野完全網羅 / クラウド完結の研究環境 / 外部 LLM ゼロを既定 /
**初版で特定マネージャの必須連携** / CLI だけで GUI を置き換えること /
**候補全件の PDF を日次で先取りすること**（ライブラリに入れたものだけ取る。ADR-0003）

## 関連の二軸（初版の芯）

利用者が登録するのは **課題意識** と **関連技術** だけである。
自分の提案手法を「類似度用に登録する」必要はない——順位は**手元に取り込んだ候補論文**を、登録した課題意識・関連技術と照らして付ける。

| 軸 | どこで | なにをする |
|---|---|---|
| **課題意識** | クラウド（Orca + 論文 API）＋ローカル採点 | `summary` を材料に、同じ問題を扱っていそうな候補を集める。Queue で時間をかけてよい |
| **関連技術** | 主にローカル（埋め込み）。収集の語彙にも使う | 分野のキーワード・技術名など。候補論文との近さで**読む順（順位）**の一部になる。採点目的で外へ送らない（`C-09`） |

利点は、時間がかかる文献調査をキューに入れておき、**起動したら調査が進んだ状態になっている**こと。
文献検索そのものにどれだけ時間がかかってもよい（NFR-01）。

### FR-05 / FR-11 の受け入れ（要約）

- 書誌（タイトル・著者・年・DOI 等）をローカルに保持・検索できる
- コレクション／タグ相当で整理できる
- 日次候補から「ライブラリに入れる」が**ワンクリック**できる
- CLI は GUI と**同じライブラリ**を読む／書く（二重管理しない）
- Electron 未起動でも CLI だけでライブラリ操作できる
- ライブラリに入れた文献が、書き出し先設定済みなら `\cite{}` できる状態になる（FR-12）
- `references/` に公開文献 PDF を置くとライブラリに入り、書誌補完のあと書き出し先設定済みなら cite できる（ADR-0003）
- Typst は Hayagriva `.yml`、TeX は `.bib`（BibTeX/BibLaTeX）
- 既存の引用ファイルに手で書いた項目が、書き出しによって壊れない（`C-08`）
- 他マネージャからの取込・双方向同期は初版必須ではない → 未決／候補

### FR-13 / FR-14 / FR-15 / FR-16 / FR-17 の受け入れ（要約）

- 収集済み候補が**課題意識・関連技術との類似度順**に並ぶ
- 各候補に「**どの関連技術に最も近いか**」が併記される。最近傍という事実であって判定ではない
- 各候補に**要旨（要約）**があり、クラウドが付けた**課題文抜粋**があれば併記する（無い・失敗は「未取得」。捏造しない）
- 採点はネットワーク不通でも実行できる（`NFR-02`）
- 採点できていない候補は「未採点」と示す。順位を捏造しない（`C-07`）
- 候補は捨てられない。順位が下でも一覧から辿れる
- 起動時（またはログイン後）に `GET /runs` で未取得分を取り込み、続けてローカル採点する
- **調査する**で自分のプロジェクトだけ Queue に投入できる。HTTP 内で論文 API / Orca を直接回さない。`summary` 空・未ログインは拒否。連打は短時間抑止する
- ライブラリの文献に PDF を添付し、アプリ内で開いてハイライト・注釈・ノートを付けられる
- **ライブラリに入れた**文献で、公開の直 PDF URL があるものはローカルへ取得する。無い・失敗は「未取得」（`C-07`）
- 注釈・ノートを付けても、添付した PDF 原本のバイト列は変わらない（`C-08`）

**初版で満たさないこと**（実測の結果。詳細は
[prototypes/judge-bench/FINDINGS.md](../prototypes/judge-bench/FINDINGS.md)）:

- **「有効／除外」の断定をしない。** 実データで類似度の閾値が引けなかった
  （有効の最小 0.7237 < 除外の最大 0.7469）
- **判定の理由を出さない。** 理由は生成 LLM が要る。小型モデルは理由を捏造したため見送った
- **「重複（競合）」と「活用」をローカル類似度だけで区別しない。** 類似度はこの 2 つを区別しない。
  どちらも高く出るため **上位には競合論文が混ざる**。利用者が読んで判断する
- **日次候補の全件 PDF 先取りはしない**（保存したものだけ。ストレージと帯域）

## 制約 (C) / 非機能 (NFR)

| ID | 内容 | ADR |
|---|---|---|
| C-01 | 未公開の恒久外部インデックス禁止。埋め込み≠プロンプト | 0001 |
| C-02 | 配布前提 | 0001,0002 |
| C-03 | 未公開を扱う機能は完全オフ可 | 0002,0003 |
| C-04 | 外部推論は分類・経路固定・同意。範囲を偽らない | 0002,0003 |
| C-05 | 分野知識をコアにハードコードしない | 0001 |
| C-06 | 開発者の有料 API キーをクライアントに置かない | 0002 |
| C-07 | 欠損≠成功表示 | 0001 |
| C-08 | **ユーザーのファイルを壊さない。**書き換えは自分の管理範囲のみ | 0003 |
| C-09 | **関連度の採点（候補論文との順位）はローカル推論で完結。**採点目的で論文・プロフィール・原稿を外部 LLM に送らない | 0001,0002 |
| NFR-01 | **日次収集と自発調査**は PC 起動に依存しない本体を持つ。いずれも Queue。**文献調査に時間をかけてよい** | 0001,0004 |
| NFR-02 | 手元検索・ライブラリ・**関連度の採点**はオフライン継続可 | 0001,0003 |
| NFR-03 | 段階縮退（C3 は秘匿優先可） | 0001,0002 |
| NFR-04 | 利用者単位の利用上限 | 0002 |
| NFR-05 | 実行時必須ランタイムを増やしすぎない（**ローカル LLM も既存の推論基盤に載せる**） | 0001 |
| NFR-06 | **採点中も UI をブロックしない**（ライブラリ・PDF 閲覧は継続可） | 0001,0003 |

スコープ外の例: Overleaf 専用橋、埋め込み API で personal を索引化、キー同梱、
**特定マネージャの必須前提**、**採点のために論文本文や原稿を外部 LLM へ送ること**、
**ローカル推論のために別プロセス／別ランタイムの導入をユーザーに求めること**、
**初版での有効／除外の断定と理由生成**、**候補全件の PDF 先取り**。
