# ADR-0013: 原稿入力をアダプタ化し (.tex / .md / .typ)、ファクトチェックを 2 段 LLM で行う

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

ゴール成功条件 4: 執筆中原稿の主張を検査できる（`FR-04` / `FR-07`）。
分類は C3（`C-03` / `C-04`、ADR-0010）。外部 LLM 利用は成功条件 5 の一部。

決めること: (1) 原稿形式 (2) 主張文の抽出方法。

### 主張文とは

本 ADR で **主張文（claim）** とは、原稿中で事実を言い切っている文を指す。
最新論文と照合して真偽が判定できる対象である。

検査対象になる例:

- 「〜をソフトウェアで実現した先行研究は存在しない」（独自性の主張）
- 「レイテンシは約 2μs である」（数値の主張）
- 「提案手法は既存手法より高速である」（比較の主張）

検査対象にならない例:

- 「本節では提案手法の評価を述べる」（構成の説明）
- 「今後の課題として大規模環境での検証が挙げられる」（展望）

前者は最新論文によって**偽になりうる**。後者は照合しても意味がない。

### 抽出方法についての方針転換

当初は「ローカルで機械的に抽出し、主張文のみを外部に送る」ことで
送信範囲を最小化する構想だった。しかし本プロジェクトは
**LLM ゲートウェイ (OrcaRouter) の活用自体を目的に含む**（ADR-0007）。
機械的抽出はその目的に逆行する。

抽出を LLM で行う場合、**抽出前は原稿のどこが主張文か分からないため、
セクション単位以上のまとまったテキストをプロンプトに載せる必要がある。**
「主張文のみを送る」は抽出段階では原理的に成立しない。

したがって ADR-0010 の C3 統制のうち「送信範囲の最小化」を
本機能には適用せず、**代わりに経路の統制と透明性を厚くする**方針に切り替える。
「送らないことで守る」から「送るが、どこに送るかを完全に統制する」への転換である。

## 決定

### 1. 原稿形式をアダプタ化する（.tex / .md / .typ を対応）

ADR-0009 の `PaperSource` と同じ方式を原稿入力にも適用する。

```ts
interface ManuscriptAdapter {
  id: string;                    // "latex" | "markdown" | "typst"
  extensions: string[];          // [".tex"] | [".md"] | [".typ"]
  /** 構造を解析し、LLM に渡す正規化テキストを返す */
  parse(entryFile: string): Promise<NormalizedManuscript>;
}

interface NormalizedManuscript {
  sections: Section[];           // 見出し階層を保ったセクション
  citations: CitationRef[];      // 既に引用が付いている箇所
  excluded: ExcludedRegion[];    // 除外した領域（数式・コメント等）
}
```

| 形式 | パーサ | 備考 |
|---|---|---|
| `.md` | `remark-parse` (unified) | 最も安定。実装の起点にする |
| `.tex` | `@unified-latex/*` (MIT) | `\input` の追跡、マクロ展開が必要 |
| `.typ` | `@typstmate/typst-syntax` (Apache-2.0) | **供給リスクあり（後述）** |

### 2. パース段階で不要な領域を落とす

LLM に渡す前に、機械的に除外する。これは送信範囲の最小化ではなく
**トークン削減と精度向上**が目的である。

- コメント（`%`、`<!-- -->`、`//`）— 執筆中のメモが含まれ、送る必要がない
- 数式環境 — 主張文の抽出に寄与せずトークンを大量に消費する
- 図表のバイナリ・パス参照、`\bibliography` の生データ
- **既に引用が付いている文は候補から除外しない**（引用が古い可能性があるため）

コメントの除外は副次的にプライバシー上も有利である
（「この主張は要確認」のような未整理のメモを外部に出さない）。

### 3. ファクトチェックは 2 段構成にする

段ごとに役割が違うため、**モデルを段ごとに固定する**（ADR-0010 の C3 統制）。

```
原稿 ──[アダプタ]──→ 正規化テキスト
                          │
              ┌───────────▼────────────┐
              │ 第1段: 主張文の抽出     │  長文入力・安価なモデルに固定
              │ (セクション単位で投入)  │  OrcaRouter: use.model = <fixed>
              └───────────┬────────────┘
                          │ 主張文リスト
              ┌───────────▼────────────┐
              │ ローカル RAG で関連論文 │  ADR-0003 / ADR-0012
              │ を引き当て (外部通信なし)│  personal + papers 空間
              └───────────┬────────────┘
                          │ 主張文 + 関連論文の要約
              ┌───────────▼────────────┐
              │ 第2段: 検証             │  判断品質優先・高性能モデルに固定
              │ (主張文ごとに判定)      │  OrcaRouter: use.model = <fixed>
              └───────────┬────────────┘
                          │
                   矛盾・要確認の指摘
```

- **第1段（抽出）**: セクション単位でまとまったテキストを投入する。
  長いコンテキストを安価に処理できるモデルに固定
- **中間（RAG）**: ローカルのみ。外部通信は発生しない
- **第2段（検証）**: 主張文単位。判断の質が要るため高性能モデルに固定

`orcarouter/auto` による自動選択は**使わない**。C3 なので上流を予測可能にする
必要がある（ADR-0010）。Routing DSL の `use: { model: ... }` で段ごとに指定する。

### 4. 入力の取得方法

- **ローカルファイル監視を主とする。** ユーザーが指定したフォルダを監視し、
  保存を契機に検査する（定期実行・手動実行の両方に対応）
- **手動アップロード・貼り付けも用意する。** 監視対象外の原稿を単発で検査できる。
  ADR-0010 の同意フローとも相性がよい
- **Overleaf は同期フォルダ経由でカバーする。** git bridge 連携は実装しない。
  有料プラン必須であり、ADR-0009 の分野非依存・配布前提と相性が悪い。
  Overleaf の同期フォルダをローカル監視対象にすれば同じ目的が達せられる

監視対象フォルダは `.gitignore` で除外済みのパス
（`manuscripts/`、`notes/`）を既定候補として提示する。

### 5. ADR-0010 の C3 統制の適用

「送信範囲の最小化」を本機能には適用しない代わりに、以下を厳格に適用する。

| 統制 | 本機能での扱い |
|---|---|
| モデル固定 | **適用。**段ごとに単一モデルへ固定 |
| 自動フォールバック無効 | **適用。**失敗時は代替プロバイダに流さずエラー |
| ガードレール | **適用。**`fail_open: false`。検証できないなら通さない |
| 明示的な同意 | **強化。**「原稿のセクション全体が送信される」と正確に提示する。
  「主張文のみ送信」と誤認させる表現を使わない |
| 送信内容のプレビュー | **必須。**実際に送るテキストを事前に確認できる |
| C3 の完全無効化 | **適用。**無効時もトレンド解析・重複判定は動く |
| 監査ログ | 機能・モデル・コスト・**セクション数**を記録。本文は残さない |

## 検討した代替案

**ローカルで機械的に主張文を抽出する** — 原稿本文が外部に出ず、
最も安全。しかし OrcaRouter の活用という本プロジェクトの目的に逆行する。
また、ヒューリスティック（引用のない断定文、数値を含む文、比較表現）では
再現率・適合率とも LLM に劣る。却下。
**ただし ADR-0011 の縮退経路として、ゲートウェイ不通時の
簡易抽出として実装する価値は残る**（別途判断）。

**ローカル LLM で抽出する** — 安全かつ精度も出るが、
モデル配布と推論環境の導入が必要で実装量が大きい。
ADR-0010 の未決事項として既に余地を残してあり、本 ADR では採用しない。

**ユーザーが検査箇所を手動選択する** — 最も安全・軽量だが、
「自動で検査する」という要件を満たさない。
ただし手動アップロード経路として部分的に取り込む。

**`.md` のみ対応する** — 実装が最も軽い。しかし研究者が LaTeX で
執筆する実態を無視することになり、「どの分野の論文を書くときにも使える」
という目標（ADR-0009）に反する。却下。

**Overleaf git bridge を実装する** — Overleaf 利用者の体験は最良。
しかし有料プラン必須で、配布時に全ユーザーが使えるとは限らない。
同期フォルダ経由で代替できるため却下。

## 帰結

**良い点**

- 3 形式に対応し、分野・執筆環境を問わず使える（ADR-0009 の目標に整合）
- アダプタ方式なので形式追加が局所的な変更で済む
- 2 段構成により、長文処理は安価に、判断は高性能モデルで行える
- 中間の RAG がローカルなので、関連論文の引き当てで外部通信が増えない
- OrcaRouter のモデル固定・ガードレールが C3 統制の実効手段として機能する

**悪い点**

- **原稿のセクション全体が外部を通る。** 上流プロバイダの保持ポリシー
  （ADR-0010 の通り OpenAI / Anthropic は約 30 日の不正利用ログ）が適用される。
  同意画面でこれを正確に伝える必要がある
- LaTeX のマクロ展開と `\input` 追跡は実装が重く、複雑な原稿で破綻しうる
- Typst パーサに供給リスクがある（後述）
- 2 段構成のため LLM 呼び出しが増え、コストが上がる
- パース失敗時の挙動（正規化できない原稿）を定義する必要がある

## Typst パーサの供給リスク

`@typstmate/typst-syntax` (Apache-2.0, v0.14.2-6) は
**Obsidian プラグイン `obsidian-typst-mate` のサブパッケージ**として
公開されており、独立して保守されるライブラリではない。
上流 `typst/typst` の `typst-syntax` の TypeScript 移植である。

リスクと対応:

- 親プロジェクトの都合で更新が止まる、または削除される可能性がある
- Typst 本体のバージョン追従が遅れる可能性がある
- **対応**: Typst アダプタは他の 2 形式と疎結合に実装し、
  パーサを差し替えられるようにする。最悪の場合、
  Typst は簡易的な行ベース解析にフォールバックする
- `research-trend` スキャンの監視対象に含める

実装の優先順位は `.md` → `.tex` → `.typ` とする。
`.md` で 2 段パイプライン全体を確立してから、パーサの差異を吸収する。

## 未決事項

- セクションが長すぎる場合の分割方針
- 検証結果の提示 UI（原稿の該当箇所へのリンク）
- パース失敗時の挙動
