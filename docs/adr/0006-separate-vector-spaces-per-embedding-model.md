# ADR-0006: 埋め込みモデルごとにベクトル空間（インデックス）を分離する

- **ステータス**: 置き換え済み (ADR-0012 による)
- **日付**: 2026-09-19

> **注記**: 本 ADR の「モデルごとに空間を分け、異空間比較を実行時エラーにする」
> という主張は ADR-0012 に継承されている。置き換えの理由は、specter2 / e5 という
> 具体的なモデル名を決定に含めていた点が分野非依存の目標（ADR-0009）と
> 両立しなかったこと、およびプロジェクト次元が欠けていたことである。
> 経緯として残す。

## コンテキスト

用途によって最適な埋め込みモデルが異なる。

**論文同士の類似検索** には学術論文特化の `allenai/specter2` が強い。引用関係で学習されているため、「引用されるべき関係にある論文」を見つける性能が汎用モデルより高く、重複研究の検出という本プロジェクトの中心的要件に直結する。

ただし specter2 には ONNX 版が公開されていない。Transformers.js から直接は使えない。

一方 **自分の未公開データ（実験ノート、原稿、メモ）** は日本語と英語が混在し、論文形式でもない。ここは `multilingual-e5-large` や `bge-m3` のような多言語汎用モデルが適する。

ここで重要な事実がある。**Semantic Scholar API は論文の specter2 ベクトルを無料で配布している。** つまり公開済み論文については、自分で specter2 を推論する必要がない。API から取得するだけで済む。

ローカルで推論が必要なのは自分の未公開データだけであり、そこは ONNX 版が存在する e5 / bge-m3 で足りる。

## 決定

**用途ごとに別のベクトル空間を持ち、決して混ぜない。**

| インデックス | モデル | 次元 | ベクトルの入手方法 | 格納対象 |
|---|---|---|---|---|
| `papers` | specter2 | 768 | Semantic Scholar API から取得 | 公開論文 |
| `personal` | multilingual-e5-large | 1024 | ローカル推論 (Transformers.js) | 未公開の研究データ・原稿・メモ |

異なるモデルが生成したベクトルは異なる空間に属するため、コサイン類似度を計算しても意味を持たない。次元数が偶然一致する場合でも同様である。したがって以下を守る。

- LanceDB のテーブルを用途ごとに分ける
- 各レコードに生成元モデルの識別子とバージョンを必ず保存する
- 検索時にクエリベクトルの生成モデルとテーブルのモデルが一致することを検証する。不一致なら実行時エラーとする

**クロス空間の比較が必要な場合**（「この新着論文は自分の実験ノートの内容と関係があるか」）は、ベクトル同士を直接比較しない。以下のいずれかで橋渡しする。

1. 論文の要約テキストを e5 で再埋め込みして `personal` 空間で検索する
2. テキストベースの手法（BM25、キーワード、LLM による判定）を使う

Semantic Scholar にベクトルが存在しない論文（未収録、プレプリント直後など）は、`papers` 空間に入れられない。この場合は要約を e5 で埋め込んで `personal` 空間側で扱うか、次回取得時まで保留にする。どちらにするかは実装時に決める。

## specter2 をローカル推論したくなった場合

Semantic Scholar に未収録の論文が多い、あるいは API 依存を減らしたい場合、以下の手順を取る。

1. Python の `optimum` で specter2 を一度 ONNX に変換する
2. 生成した ONNX ファイルを成果物として配布に同梱する
3. 以降の推論は Transformers.js のみで完結する

この場合 Python は**ビルド時ツール**であり、ADR-0005 の「Python を実行時の必須依存にしない」に反しない。

## 検討した代替案

**単一モデル (e5 のみ) で統一する** — 空間管理が単純になり、クロス空間問題が消える。しかし論文間の類似検索という中心機能で specter2 の性能を捨てることになる。加えて Semantic Scholar が無料で配っているベクトルを使わない理由がない。却下。

**specter2 のみで統一する** — 日本語混在の未公開データに対して性能が出ない。specter2 は英語論文のタイトル+要約で学習されている。却下。

**ベクトルの次元を揃えて同一テーブルに入れ、モデル列でフィルタする** — 実装上は可能だが、フィルタ漏れで異空間比較が起きた場合に「エラーにならず、静かに無意味な結果を返す」という最悪の失敗をする。テーブル分離で構造的に防ぐ。却下。

## 帰結

**良い点**

- 各用途で最良のモデルを使える
- 公開論文の specter2 ベクトルを API から得られるため、ローカル推論の負荷が未公開データ分のみに収まる
- テーブル分離により異空間比較を構造的に防げる

**悪い点**

- インデックスが複数になり、管理とマイグレーションが複雑になる
- クロス空間の比較に橋渡しが必要で、そのための再埋め込みが追加コストになる
- Semantic Scholar API への依存が生じる。レート制限と、ベクトル未収録論文への対処が必要
- 将来モデルを変更する場合、該当インデックスの全再構築が必要になる
