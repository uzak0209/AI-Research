# ADR-0003: RAG はローカル完結とし、埋め込みもローカルで推論する

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

要件に「自分の研究データや過去のデータは RAG にしておきたい」がある。対象となるのは以下のようなデータである。

- 未公開の実験データ・測定結果
- 実験ノート、進捗メモ
- 書きかけの原稿（投稿前）
- 過去に自分が読んだ論文のメモ

これらは**公開前の研究成果**であり、先行性が価値を持つ。外部サービスへの送信は、利用規約上の学習利用の可否とは別に、リスクとして扱うべきである。

RAG の構築は3つの工程に分解できる。それぞれ独立に配置先を選べる。

| 工程 | 内容 | 外部送信の有無 |
|---|---|---|
| ① チャンク分割 | PDF/tex を数百〜千字程度に分割 | 純粋なテキスト処理。発生しない |
| ② 埋め込み生成 | テキスト → ベクトル | **選択次第で発生する** |
| ③ 保存・近傍検索 | ベクトル DB への格納と検索 | ローカル DB なら発生しない |

つまり外部送信が起きうるのは ② のみである。

## 決定

**RAG を全工程ローカルで完結させる。**

- **② 埋め込み生成**: ローカル埋め込みモデルを Transformers.js (ONNX Runtime) で実行する。埋め込み API (Voyage AI, OpenAI embeddings 等) は使わない
  - 第一候補: `Xenova/multilingual-e5-large` (1024次元、日英混在に強い)
  - 代替: `Xenova/bge-m3` (多言語、長文に強い)
  - 初回のみモデルを取得してキャッシュし、以降はオフラインで動作する
- **③ ベクトル DB**: LanceDB (`@lancedb/lancedb`) をローカルファイルとして持つ
- **研究データの恒久的なインデックスをクラウドに作らない**

RAG 検索はデスクトップアプリ起動中にのみ使用するため、クラウドに置く必要がそもそもない。この決定によって機能的な制約は生じない。

### この決定の適用範囲（重要）

本 ADR が禁じているのは **「未公開データの恒久的なインデックスを外部に作ること」** である。
未公開データを含むテキストを、都度の推論のために外部へ送ることまで禁じてはいない。

この区別は意図的なものであり、ADR-0010 で LLM 推論について別途判断している。
両者を分ける根拠は次の非対称性にある。

| | 埋め込み API | LLM 推論（プロンプト） |
|---|---|---|
| 送るデータ | **全データを網羅的に** 送る（RAG 構築時に全件） | その処理に必要な範囲のみ、都度 |
| 外部に残るもの | ベクトルが**恒久的なインデックス**として蓄積される | 送信時点のリクエストのみ（保持ポリシーに依存） |
| 中止した場合 | 既に作られたインデックスは残る | 以降送らなければ増えない |
| ユーザーの認識 | 意識されない（バックグラウンドで全件処理） | 機能を実行した時点で意識できる |

「全データを網羅的・恒久的に外部へ蓄積する」ことと「必要な分を都度送る」ことは、
リスクの性質が異なる。前者は一度実行すると取り返しがつかず、かつユーザーが
意識しないまま進行する。したがって埋め込みはローカルに限定し、LLM 推論は
ADR-0010 の統制（データ分類・プロバイダ固定・同意）の下で外部を許容する。

**この非対称性を曖昧にしてはいけない。** 「LLM に送るなら埋め込みも送ってよい」
という推論は本 ADR の意図に反する。逆に「埋め込みを送らないから LLM にも送らない」
も本 ADR の主張ではない。

## 検討した代替案

**埋め込み API を使う** — 精度とセットアップの容易さで優位。費用も論文数千本規模なら数百円程度で無視できる。しかし未公開データが外部に出るため却下。なお Anthropic は埋め込み API を提供していないため、この選択肢は必然的に他社サービスになる点も判断材料になった。

**Cloudflare Vectorize にベクトルを置く** — クラウド側の cron でも自分の研究との照合ができる利点があった。しかしベクトルは元テキストの情報を相当量保持しており、埋め込み逆変換攻撃の研究例もあるため「ベクトルなら安全」とは扱わない。却下。クラウド側での粗い照合は ADR-0004 の研究プロフィール方式で代替する。

**ハイブリッド（公開論文は Vectorize、未公開データはローカル）** — 機能的には最良だが、2つのストアの整合性管理と検索結果のマージが複雑になる。初期構成としては過剰。将来的に公開論文のインデックスが大きくなりすぎた場合に再検討する。

## 帰結

**良い点**

- 未公開の研究データの**恒久的なインデックスが外部に作られない**
  （LLM 推論としての都度送信は ADR-0010 の統制下で別途許容する）
- 埋め込み費用がゼロ。データ量が増えても費用が増えない
- オフラインで RAG 検索が動く
- API のレート制限やサービス終了に影響されない

**悪い点**

- モデルのダウンロードが 1〜2GB 程度必要（量子化で削減可能）
- 初回起動時にモデル取得の待ち時間が発生する。UX 上の配慮が必要
- 商用埋め込み API に比べて検索精度がやや劣る可能性がある。実データで評価してモデルを選び直せる余地を残す
- インデックス再構築（モデル変更時など）に CPU/GPU 時間がかかる
