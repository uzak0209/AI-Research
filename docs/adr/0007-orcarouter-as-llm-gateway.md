# ADR-0007: LLM 呼び出しを OrcaRouter ゲートウェイ経由に統一する

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

本システムは 3 箇所で LLM 推論を必要とする。

1. トレンド解析（クラウド cron、ADR-0002）
2. 新着論文と自分の研究の重複・関連性判定（デスクトップ、ADR-0004 第二段）
3. 執筆中原稿のファクトチェック

これらを各プロバイダの SDK で直接実装すると、プロバイダごとに認証・リトライ・
エラー処理が分散し、障害時のフェイルオーバーを自前で書くことになる。
また、どのモデルにいくら使ったかの把握も自前になる。

OrcaRouter は 1 つの OpenAI 互換エンドポイントで 150 以上の上流モデルを扱う
AI ゲートウェイであり、アダプティブルーティング、自動フェイルオーバー、
ガードレール、エージェントファイアウォール、リクエスト単位の可観測性を
同一エンドポイントで提供する。

## 決定

**すべての LLM 呼び出しを OrcaRouter 経由に統一する。** 各プロバイダの
SDK を直接呼ばない。

- エンドポイント: `https://api.orcarouter.ai/v1`（OpenAI 互換）
- 認証: API キー。**スコープ付きキー**を用途ごとに発行する（後述）
- アプリケーション側は OpenAI 互換クライアントを 1 つ持つだけでよい

### 用途ごとにスコープ付きキーを分離する

OrcaRouter は「自分の上限・予算・失効を持つスコープ付きキー」を発行できる。
これを用途の境界に合わせて発行し、1 つのキーを共用しない。

| キー | 用途 | 特性 |
|---|---|---|
| `cron` | 日次トレンド解析 | 公開論文のみを扱う。予算上限を日次消費量に合わせる |
| `interactive` | ユーザー操作による判定 | ユーザー単位のレート制限を BFF 側で併用（ADR-0008） |
| `sensitive` | 未公開データを含む処理 | 許可モデルを固定。ガードレールを厳格化（ADR-0010） |

キーを分ける目的は、**1 つのキーの漏洩・暴走が他の用途に波及しないこと**、
および用途ごとにコストを把握できることである。

### ルーティングは用途に応じて固定するか自動に任せるかを分ける

OrcaRouter は `orcarouter/auto` による自動選択、`extra_body.models` による
フォールバックチェーン、Named Router と Routing DSL による細かい制御を持つ。

- **公開論文のみを扱う処理**: コスト最適化を優先し、自動選択・フォールバックを活用する
- **未公開データを含む処理**: モデルを明示的に固定する。ADR-0010 で規定する

Routing DSL では `use: { model: "..." }` で単一モデルへの固定、
`use: { models: [...] }` で許可リスト、`use: { pool: "@pool:<name>" }` で
管理者が定義したプールへの制限ができる。Router レベルの
**Allowed models glob** が安全境界として機能する。

なお `channels:` / `@channel:` によるチャネル固定は現時点で未提供であり、
lint で unsupported として扱われる。**上流の物理的な経路までは固定できない**
ことを前提に設計する。

## 検討した代替案

**各プロバイダの SDK を直接使う** — ゲートウェイへの依存が無くなり、経路が単純。
しかしフェイルオーバー、コスト集計、ガードレールをすべて自前で実装することになる。
今回はゲートウェイの活用自体が目的でもあるため却下。ただし ADR-0011 で
ゲートウェイ障害時の退避を規定し、ロックインを緩和する。

**自前で薄い抽象化層を書く** — 抽象化の自由度は高いが、実質ゲートウェイの再実装になる。
`<50ms` のミッドストリームフェイルオーバーや PII マスキングを自作する価値は無い。却下。

## 帰結

**良い点**

- プロバイダ追加・切り替えがアプリ側の変更なしでできる（ADR-0009 の抽象化方針と整合）
- 自動フェイルオーバーにより単一プロバイダの障害で機能停止しない
- リクエスト単位でモデル・レイテンシ・コストが取れるため、コスト管理の土台になる
- トークンあたりのマークアップが 0 で、各プロバイダの公表価格で課金される
- ガードレール（PII Shield）とエージェントファイアウォールをゲートウェイ層で適用できる

**悪い点**

- ゲートウェイが単一障害点になる。ADR-0011 で退避を規定する
- 全プロンプトがゲートウェイを通過する。データ扱いの検討が必須（ADR-0010）
- 上流プロバイダの選択が自動ルーティングで変わりうるため、
  未公開データを含む処理では明示的な固定が必要（ADR-0010）
- チャネル固定が未提供のため、上流の物理経路は制御できない

## 検証した事実（2026-09-19 時点）

以下は公式サイト・ドキュメントで確認した。前提が変わりうるため
`research-trend` スキャンの監視対象とする。

- OpenAI 互換エンドポイント、OpenAI / Anthropic / Google SDK がそのまま動く
- トークンマークアップ 0、各プロバイダの公表価格
- スコープ付きキー（個別の上限・予算・失効）
- ガードレール（PII Shield）はマスク既定、上流到達前に適用される
- SOC 2 / GDPR / HIPAA / ISO 27001:2022（レポートは NDA 下で提供）
- **ゼロデータ保持は OrcaRouter 自社サーバのみが対象**（ADR-0010 で詳述）
