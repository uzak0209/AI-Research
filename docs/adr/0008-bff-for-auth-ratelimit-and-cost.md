# ADR-0008: BFF を挟み、認証・レート制限・コスト統制をサーバ側で行う

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

ゴールは配布前提（`C-02`）。成功条件 5 のため LLM は OrcaRouter に統一した（ADR-0007）が、
認証は API キーのみである。制約 `C-06`: 開発者の有料キーをクライアントに置けない。

同梱すれば抽出され、課金が開発者に来る。加えて利用者単位のレート制限・コスト上限・失効が必要（`NFR-04`）。
Zotero OAuth の Client Secret も同じ BFF に置く（ADR-0015）。

## 決定

**BFF (Backend for Frontend) を Cloudflare Workers 上に置き、
デスクトップから OrcaRouter を直接呼ばない。**

```
Electron ──(OAuth アクセストークン)──→ BFF (Workers) ──(API キー)──→ OrcaRouter ──→ 各プロバイダ
              ユーザーを識別                  キーはここだけが保持
```

### 認証

- **OAuth 2.0 (GitHub / Google) + PKCE**。デスクトップアプリなので
  クライアントシークレットを秘密にできない前提で PKCE を必須とする
- 自前でパスワードを保持しない（漏洩面を持たない）
- 認可コードの受け取りはループバックリダイレクト（`http://127.0.0.1:<random>/callback`）。
  カスタムスキームは他アプリが奪える余地があるため使わない
- BFF は短命のアクセストークン（15 分程度）とリフレッシュトークンを発行する
- トークンは **OS の secure storage**（macOS Keychain / Windows Credential Manager）に保存し、
  平文でディスクに置かない

### キーの保持場所

- OrcaRouter の API キーは **Workers Secrets にのみ**置く。
  リポジトリ、クライアント、ログのいずれにも出さない
- ADR-0007 のスコープ付きキー（`cron` / `interactive` / `sensitive`）を
  BFF が用途に応じて使い分ける。クライアントはどのキーが使われたかを知らない

### レート制限

- ユーザー単位・エンドポイント単位で制限する（Durable Objects または
  Workers KV + タイムウィンドウ）
- 制限値は「通常利用では当たらず、暴走時には必ず当たる」水準に置く
- 429 応答には `Retry-After` を付け、クライアントは指数バックオフで従う
- **OrcaRouter 側のレート制限に依存しない。** ゲートウェイの制限はキー単位であり、
  ユーザー単位の公平性を担保しない

### コスト統制

- ユーザーごとに期間内の消費上限を持つ。上限到達時は 402 相当を返して停止する
- OrcaRouter のスコープ付きキーの予算上限を**二重の防護**として併用する。
  BFF のバグで無制限に呼んでも、キーの予算上限で止まる
- リクエスト単位のコストを記録する（OrcaRouter がモデル・レイテンシ・コストを返す）

### 監査ログ

- 記録する: 誰が / いつ / どの機能を / どのモデルで / いくら / 成否
- **記録しない: プロンプト本文と応答本文。** 未公開の研究データを
  こちらのログに蓄積してしまえば、ADR-0003 の原則を BFF が破ることになる
- 障害調査にはリクエスト ID による OrcaRouter 側の相関を使う

## 検討した代替案

**BYOK（各ユーザーが自分の OrcaRouter キーを入れる）** — 開発者が他人の課金も
データも預からないため、責任範囲が最小になる。ADR-0003 の原則とも最もよく整合する。
しかし全ユーザーに OrcaRouter アカウント作成を要求し、オンボーディングが重い。
配布を前提とする本システムでは採用しない。
ただし**将来の選択肢として残す**（ADR-0011 の退避経路としても機能する）。

**キーを同梱して難読化する** — 上述の通り必ず破られる。却下。

**デバイストークンのみ（OAuth なし）** — 実装は軽いが、デバイス単位では
同一ユーザーの複数デバイスを束ねられず、コスト上限が実質無効になる。却下。

## 帰結

**良い点**

- OrcaRouter のキーがクライアントに一切出ない
- ユーザーを識別できるため、レート制限・コスト上限・個別失効が成立する
- ADR-0002 で既に Workers を使っているため、インフラが増えない
- BFF がプロバイダ差異を吸収するため、クライアントの実装が薄くなる

**悪い点**

- BFF 自体が攻撃対象かつ単一障害点になる
- 認証・トークン更新・失効・レート制限の実装と運用が必要になり、実質 SaaS 運営になる
- オフラインで LLM 機能が使えない（ローカル RAG 検索は ADR-0003 通りオフライン可）
- 開発者がユーザーの利用状況を（本文は持たないとしても）把握する立場になる。
  プライバシーポリシーでの明示が必要
- ユーザー数に比例して LLM コストが開発者に来る。上限設計を誤ると請求が跳ねる

## セキュリティ上の留意点

- BFF は**プロキシであって自由な中継ではない**。クライアントから任意のモデル名や
  任意のプロンプトテンプレートを受け取って上流に流すと、
  第三者が汎用 LLM プロキシとして悪用できる。
  **許可された機能（トレンド解析・重複判定・ファクトチェック）ごとに
  エンドポイントを分け、プロンプトの骨格はサーバ側が持つ**
- クライアントから来るのは入力データとパラメータのみ。モデル選択は BFF が決める
- リフレッシュトークンは失効リストを持ち、ローテーションする
- CORS は不要（デスクトップからの呼び出し）。ブラウザからの利用を想定しない
