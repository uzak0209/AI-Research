# ADR-0011: 外部依存の障害時は機能を段階的に縮退させ、無言で失敗しない

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

ゴール成功条件の欠損可視化（制約 `C-07` / `FR-08`）と `NFR-03`。
外部依存（OrcaRouter・BFF・D1・論文ソース・Zotero）はどれも落ちうる。
成功条件 1〜6 のうち、落ちた依存だけを欠けさせ、残りは動かす。

| 依存 | 落ちたときに影響する機能 |
|---|---|
| OrcaRouter（ADR-0007） | すべての LLM 機能 |
| BFF / Workers（ADR-0008） | すべてのクラウド機能 |
| D1（ADR-0002） | 日次レポートの蓄積と同期 |
| 論文ソース API（ADR-0009） | 該当ソースからの収集 |
| Semantic Scholar（ADR-0012） | 論文ベクトルの取得 |
| Zotero | 参考文献の保存 |

特に注意すべき性質が 2 つある。

**1. 日次 cron は誰も見ていない時間に走る。** 失敗しても気付かれない。
ADR-0002 の「アプリを閉じていても動く」という利点が、
そのまま「失敗しても分からない」という欠点になる。

**2. 部分的な失敗が最も危険。** 論文ソースの 1 つが落ちた状態で
「今日は新着 0 件」と報告すると、**取りこぼしを成功と誤認する。**
ADR-0004 の第一段フィルタは緩い閾値で再現率を優先する設計なので、
ソースが欠けた事実が隠れると設計意図が崩れる。

## 決定

### 1. 縮退の段階を定義する

機能を全部止めるのではなく、段階的に縮退させる。

| 障害 | 縮退後の挙動 |
|---|---|
| OrcaRouter 全体が不通 | 論文の**収集とメタデータ保存は継続**し、LLM 解析のみ欠落としてマークする。後日の再解析キューに入れる |
| 特定プロバイダが不通 | C1/C2 はフォールバックで継続（ADR-0007）。**C3 はフォールバックせずエラー**（ADR-0010） |
| BFF が不通 | デスクトップは**ローカル RAG 検索と過去レポート閲覧を継続**（ADR-0003 の通りオフライン可） |
| D1 が不通 | cron は失敗を記録してリトライ。デスクトップは取り込み済みデータで動作 |
| 論文ソースの一部が不通 | **他ソースで継続。ただしレポートに「どのソースが欠けたか」を必ず明記** |
| Semantic Scholar が不通 | ベクトル取得を保留し、識別子のみ保存。後日補完 |
| Zotero が不通 | 保存操作をローカルキューに積み、復旧後に再送 |

### 2. 「欠損」を成功と区別する

**レポートは必ずデータ源の網羅性を含む。**

- 各ソースの取得成否と件数
- 欠けたソースがある場合はレポート冒頭に明示
- LLM 解析が欠落した項目はその旨をマーク

「新着 0 件」と「ソース障害により取得できず 0 件」を**同じ表示にしない。**
これは ADR-0004 の「第一段で落とした件数を可視化する」緩和策と同じ思想である。

### 3. 無言の失敗を禁じる

cron が失敗したら記録し、デスクトップ起動時に**必ず気付ける形で提示**する。
この方針は既に `.github/workflows/claude.yml` のフォールバック
（無言で終わった場合にコメントを残す）で同じ問題に対処しており、
システム全体の原則として採用する。

- 失敗した日は「失敗した」と分かる状態でレポート履歴に残す。欠落を空白にしない
- 連続失敗が閾値を超えたら、起動時に警告する

### 4. リトライは冪等性を前提に設計する

- レポートには一意 ID を振る（ADR-0002 の未決事項として挙がっていた点）
- デスクトップ側は取り込み済みカーソルを持ち、二重取り込みを防ぐ
- リトライは指数バックオフ + ジッター。上流のレート制限（429）は `Retry-After` に従う
- **cron の再実行で同じ日のレポートが重複生成されないこと**を保証する

### 5. ロックインを緩和する

ADR-0007 でゲートウェイに依存すると決めたが、退避経路を残す。

- アプリケーションから見た LLM 呼び出しは**OpenAI 互換インターフェース**に閉じる。
  OrcaRouter 固有の機能（Routing DSL、Named Router）は BFF 内に局所化する
- これにより、ゲートウェイを別のものに差し替える、あるいは
  プロバイダを直接呼ぶ構成に退避することが、BFF の変更のみで可能になる
- ADR-0008 で却下した BYOK も、この退避経路として機能する

## 検討した代替案

**障害時は全機能を停止する** — 実装が単純で、部分的な結果による誤認も起きない。
しかし論文収集は継続できるのに止めるのは損失が大きい。
「欠損を明示する」ことで誤認は防げる。却下。

**リトライを無制限にする** — 一時障害には強いが、恒久的な障害
（API 廃止、認証失効）でリトライを続けてコストとレート制限を消費する。
上限を設けて失敗として記録する方を選ぶ。却下。

**LLM 解析が失敗したらその日のレポートを作らない** — 一貫性はあるが、
論文の新着情報という価値ある部分を捨てることになる。
解析欠落をマークして保存する方を選ぶ。却下。

## 帰結

**良い点**

- 単一の外部依存の障害で全体が止まらない
- 「取りこぼしを成功と誤認する」という最も危険な失敗を構造的に防ぐ
- オフラインでもローカル RAG と過去レポートが使える
- ゲートウェイへのロックインが BFF に局所化される

**悪い点**

- 縮退の段階ごとに実装とテストが必要になる。障害注入テストの整備が前提
- レポートに網羅性の情報が増え、表示が複雑になる
- 再解析キューという追加の状態を持つことになる
- 冪等性の担保（一意 ID、カーソル管理）に設計コストがかかる
