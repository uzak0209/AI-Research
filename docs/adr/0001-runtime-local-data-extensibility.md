# ADR-0001: 実行形態・ローカルデータ・拡張点

- **ステータス**: 承認済み / **日付**: 2026-09-19（改訂 2026-09-20: 採点をローカル埋め込みに確定し、生成 LLM を見送り／同日: ローカル RAG 節の陳腐化した記述〔重複・競合のローカル LLM 判定〕を削除し整合／改訂 2026-09-21: `references/` への OA 直リンク取得を例外として明記／同日: 関連の二軸と起動時プルを明記／同日再改訂: 登録面を課題意識＋関連技術に確定／同日再々改訂: 読む順は `mypaper/`↔候補 PDF 全文を優先。空なら課題意識＋関連技術にフォールバック／**同日 4 回目改訂: 「生成 LLM を初版で使わない」はローカル実行に限ると明記（ADR-0005 #40）**／**改訂 2026-09-22: テーマとトレンドは収集 1 回の公開論文から出し、報告として保存する。mypaper に置いた PDF は読む順の材料にもする**）
- **要件**: FR-01〜03, FR-06, FR-09, FR-13, FR-15, NFR-01/02/05/06, C-01, C-05, C-07, C-09

## 決定

### 二層

| | クラウド (Workers Cron + D1) | デスクトップ (Electron + TS) | CLI（共有コア） |
|---|---|---|---|
| 役割 | **課題意識に近い候補**の日次収集・粗い足切り・課題文抜粋・**その回のトレンドと次テーマ**・蓄積 | プル同期、**候補論文との類似順位**、報告 UI、ライブラリ、My paper、FC | ライブラリ等 |
| データ | 公開のみ（研究プロフィール＝`summary`＝課題意識＋関連技術の収集面） | 未公開 RAG・原稿・**ライブラリ** | **同じローカルストア** |

同期は起動時プル（`GET /runs`）が主。`summary` のクラウド反映は収集材料の同期であり、**判定の書き戻しではない**（C-01）。
Python は実行時必須にしない。Workers と型・スキーマ共有。
GUI と CLI は共有コア越しに同一データを触る（二重管理しない）。

### 関連の二軸

利用者が登録するのは **課題意識** と **関連技術** である（収集の材料）。
**読む順**の正本は作業フォルダの `mypaper/` 原稿（あれば）。空のときだけ課題意識・関連技術にフォールバックする。
未公開の提案手法をクラウドへ載せる必要はない（`C-01`）。

| 軸 | 場所 | 材料 | 出すもの |
|---|---|---|---|
| **課題意識** | クラウド＋ローカル | `summary`（問題・問い） | 同じ問題を扱っていそうな候補。`mypaper/` 空時の読む順にも使う |
| **関連技術** | 主にローカル（収集語彙にも載せる） | キーワード・技術名（1 行ずつ） | `mypaper/` 空時の読む順の一部。有効／除外は断定しない |
| **`mypaper/` 原稿と自分の論文** | ローカルのみ | `.md` / `.tex` / `.typ`、自分の PDF | あれば読む順の正本。原稿はクラウドへ出さない。PDF を置いたときだけ公開書誌（C1） |

### 関連度の採点（FR-02, FR-13, C-09）

**候補論文との順位付けはローカル推論で完結する。採点を外部 LLM に任せない。**
候補を全件・毎日外へ出すのは `C-01` の趣旨に反する。

**初版は順位付けだけを行い、有効／除外を断定しない。**

| 段 | 場所 | 手段 | 出すもの |
|---|---|---|---|
| 1 粗選別 | クラウド | 検索語（Orca）＋文字列一致（ADR-0004） | 課題意識に寄せた候補 |
| 1b 課題文 | クラウド | 安価モデルで要旨から課題・問題の文を抜く（ADR-0005） | `problem_excerpt`（順位ではない） |
| 2 採点 | ローカル | **埋め込み（Transformers.js）** | **関連度と順位** |

採点式（優先）:

1. **`mypaper/` に実質の原稿がある** → 原稿チャンク ↔ 候補 PDF 本文チャンクの **max cos**。
   PDF 本文が取れない候補は**未採点のまま**（タイトル＋要旨で埋めない）
2. **`mypaper/` が空** → フォールバック **`blend` = 課題意識 cos × 0.7 ＋ 最近傍の関連技術 cos × 0.3**
   （論文はタイトル＋要旨。PDF 不要）

- フォールバック時は各論文に**最も近い関連技術**を併記する。最近傍という**事実**であって判定ではない
- `mypaper/` ありのときは UI に「原稿との近さ」を残す（`sim_summary` 相当）
### 閾値を引かない（C-07）

実データでは有効／除外の類似度が重なり、**閾値では分離できなかった**
（有効の最小 0.7237 < 除外の最大 0.7469。[FINDINGS.md](../../prototypes/judge-bench/FINDINGS.md)）。

- **順位だけを出し、線は引かない。** 引けないものを引いたふりをしない
- 候補は捨てない。順位が下でも一覧から辿れる
- 採点できていない候補は「未採点」と示す。順位を捏造しない

### ローカルでは生成 LLM を初版で使わない

3 段目として小型の生成 LLM を検討し、実測のうえ**見送った**。
**この見送りはローカル実行に限る。**クラウド側は課題文の逐語抜粋という限定された形で
生成 LLM を使う（`problem_excerpt`。ADR-0005）。判断・理由文の生成はローカルでもクラウドでもしない。

- Qwen2.5-**0.5B** q4 は precision 0.324 で、**useful の基準率 0.32 と一致**した（偶然と区別がつかない）。
  さらに**論文に書かれていない内容を理由文に生成**した。`C-07` に反する
- Qwen2.5-**1.5B** q4 は合成データで 20/20 一致したが、1 件 18 秒かかり、
  最低要求スペックを引き上げる。実データでの検証前に見送りを決めた
- 埋め込みは 1 件 80 ms。**生成 LLM は約 200 倍重い**

見送りの代償は要件に明記してある（理由を出さない／重複と活用を区別しない）。

### 実行形態（NFR-06）

- 採点は**起動後にバックグラウンドで走らせ、その間もライブラリと PDF ビューアを使えるようにする**
- **レンダラで回さない。** Electron の `utilityProcess`（標準 API。ランタイムを増やさない）で実行する
- 1 件ごとに DB へ確定させ、UI は差分を購読して逐次反映する。
  途中で閉じても済んだ分は残り、残りは未採点のまま次回に回る（再開用のキュー表は要らない）
- **楽観的 UI（採点前の順位を推測して見せ、後で覆す）は採らない**（`C-07`）

実測では 50 件 4.2 秒（起動時 0.2 秒＋ 1 件 80 ms）。同期でも耐えられる水準だが、
件数が増えたときに UI を塞がない形を最初から取る。

### クラウドで LLM を使って利用者向け順位を付けない

実測で、**明確に無関係な候補はローカルの順位付けで既に下位に沈んでいた**。
それらを除いても利用者が読む上位の集合は 1 件も変わらなかった。
ローカルの採点は 1 件 80 ms で済むため、クラウドで LLM に課金して**最終順位を決める**根拠がない。
ADR-0004 の「粗い採点は文字列一致に留める」を維持する。
**課題意識に寄せた収集・課題文抜粋は順位付けではない**（ADR-0005）。

### テーマ候補（FR-09）

テーマ候補と今のトレンドは、**その収集で残した公開論文**から出す（cron も自発調査も同じ）。原稿・課題意識の未公開詳細は載せない（C-01, C-09）。分類は C1。`POST /theme`（C2）は初版では閉じたまま。

結果は実行行に残し、デスクトップは **1 報告 = いつ・トレンド・次テーマ・見つけた論文** で見せる。欠けたら「未着」と出す（C-07）。

### ローカル RAG

- 埋め込みはローカルのみ（Transformers.js / ONNX Runtime）。埋め込み API 禁止。
  **ローカル推論はこの 1 つの基盤に閉じる**（`NFR-05`）
- ローカル保存は SQLite 1 ファイル＋`sqlite-vec`（組込み・サーバー不要）。メタとベクトルを同一トランザクションで扱う
- 1 プロジェクト = やりたいこと 1 つ = 埋め込みモデル 1 つ。モデル変更時は再索引。未公開データはローカル推論のみ
- 論文ベクトルは保存せず判定時に同モデルで計算。モデルは設定（分野名をコードに埋めない）
- クラウドに出すユーザー情報は**課題意識と関連技術をまとめた `summary` のみ**（未公開の提案手法・原稿は載せない）

### データ配置（ER 図は [er-diagram.md](../er-diagram.md)）

境界: **クラウドは「誰の・どのプロジェクトに・いつ・何が集まったか」まで。
論文への判断と手元の文章はローカル。**

- クラウドに出るユーザー情報は**`summary`（課題意識＋確認済みキーワード）のみ**。
  日次収集が何を集めるか判断する唯一の材料であり、同時に唯一の流出面
- クラウドは**ユーザー名・メールを持たない**。本人確認は OAuth subject のみ
- **クラウドに論文マスタ表を作らない。** 収集実行の行に論文情報を直接持つ。
  実行ごとに重複するが、結合を減らし保持期間の管理を単純にする
- 収集実行は `ok / empty / failed / partial` を区別し、欠けた依存だけを記録する（`FR-08`, `C-07`）
- 同期位置はローカルのプロジェクト行が持つ（`last_run_id`）。設定には置かない
- 1 プロジェクトは作業フォルダを持てる（未設定可）。

  ```
  {root}/
    references/   # 文献 PDF。利用者が置く。ライブラリ分の OA 取得もここ（ADR-0003）。既存は上書きしない
    candidates/   # 採点用の候補 PDF（ライブラリ行は作らない）。既存は上書きしない
    mypaper/      # 自分の原稿と論文（FR-07・読む順の正本。PDF は書誌も作る）
    claims/       # 関連技術の作業用フォルダ名（中身は技術・キーワード行）
  ```

  索引の正本は SQLite。フォルダはユーザーのファイル置き場。
  空でない既存フォルダには作らない（`C-08`）。利用者が既に持っている PDF を勝手に動かさない。
  OA 取得は `candidates/`（採点）と `references/`（ライブラリ）に足すだけで、既存は上書きしない（ADR-0003）
- 判定結果・ライブラリの保存状態は行が自分で持つ。**別のキュー表を作らない**
- 秘密（更新トークン等）は OS の保護領域に置く。Electron は `safeStorage`
  （macOS Keychain / Windows DPAPI / Linux libsecret）。`localStorage` も
  httpOnly Cookie も使わない。GUI と CLI が同じストアを読む（FR-11, NFR-05）
- **更新トークン**は保護領域に残す。再起動後もこれで access を取り直す
- **アクセストークン**は短命 JWT。ディスクには置かずメモリのみ（メインプロセス）。
  レンダラは IPC 経由で API を呼び、トークンそのものを持たない
- **DB ファイル自体は暗号化されない**——同一 PC の同一ユーザー権限からは
  `safeStorage` の復号はできる。保護の対象は「ファイルを見ただけでは読めない」こと

保存しないもの: FC 結果（未決）、
埋め込み空間表（プロジェクト行の 1 モデルで足りる）。
テーマ候補とトレンドは実行行（クラウド `runs` / ローカル `survey_reports`）に残す。

### 拡張

- 論文ソースはアダプタ + `capabilities`。プロジェクト／`user_id` 次元を最初から持つ

### 障害

- 欠けた依存だけ欠落表示。「0件」と「取得失敗」を区別。レポートは一意 ID
- LLM は OpenAI 互換に閉じ、差替えは BFF 内に局所化

却下:

- ローカル cron のみ / クラウド完結 / personal を外部索引化
- SQLite＋LanceDB 併用（ネイティブ依存 2 つ・二重ストア整合）
- **採点を外部 LLM に任せる**（候補が全件外に出る。`C-09`）
- **重複／活用をローカル LLM で精密ラベル付けする**（「生成 LLM を初版で使わない」と矛盾し実測もない。
  初版は区別しない。次版で入れるかは [requirements.md](../requirements.md) の未決事項）
- **node-llama-cpp / Ollama を入れる**（前者はネイティブ依存と OS ごとの prebuild、
  後者はユーザーの別途インストールが前提になり `C-02` と釣り合わない。`NFR-05`）
- **類似度に閾値を引いて有効／除外を断定する**（実データで分離できなかった。`C-07`）
- **関連技術だけで採点する**（課題意識を外すと精度が落ちた。1 行ずつのため、
  どれか 1 つへの偶発的な食いつきで順位が跳ねる）
- **候補を捨てる**（取りこぼしに気づけない。`C-07`）

## 実測（2026-09-20 / i5-1334U・CPU のみ）

[prototypes/judge-bench/FINDINGS.md](../../prototypes/judge-bench/FINDINGS.md)。
実データは OpenAlex から取得した 50 件（明確に関連 14 / 境界 24 / 明確に無関係 12）。

| 採点式 | 取りこぼしゼロに必要な上位件数 |
|---|---|
| **blend（採用）** | **17 / 50（34 %）** |
| summary のみ | 19 / 50（38 %） |
| 主張のみ | 22 / 50（44 %） |

- 1 件 80 ms。50 件 4.2 秒。採点式による差は起動時の 189 ms だけで、件数に依らない
- 処理時間の 94.5 % は論文の埋め込み。内積の回数は誤差以下
- 有効 16 件のうち 14 件が 1〜14 位を占め、揺れは 15〜21 位の帯に収まった

数字は n=50・プロジェクト 1 件・埋め込みモデル 1 種の結果で、法則ではない。

## 未決

- `mypaper/`↔全文 max-cos の実データでの取りこぼし（採用式の検証は従来 blend）
- 有効／除外の断定と理由生成を次版で入れるか。入れるなら最低要求スペックの表明が要る
- 日本語の要旨・日本語プロフィールでの精度（未計測）
- 埋め込みモデルの既定と、モデル変更時の再索引 UX
- 件数が数千件に増えたときの検索速度（sqlite-vec に載せてから測る）
