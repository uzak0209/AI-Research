# ADR-0004: 関連度判定を「クラウドで粗く、ローカルで精密に」の二段フィルタにする

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

ADR-0002 で定期実行をクラウドに、ADR-0003 で RAG をローカルに置くと決めた。この2つの組み合わせから、直接的な矛盾が生じる。

> クラウド側の cron は、ローカルの RAG を参照できない。
> したがって「この新着論文は自分の研究と被っているか」の精密な判定を、クラウド側では実行できない。

一方でクラウド側は何らかの絞り込みを行う必要がある。arXiv の新着は分野によって1日数百件に及び、全件をそのまま D1 に保存してデスクトップに流すと、同期が重くなりレポートとしても読めない。

## 決定

関連度判定を2段階に分ける。

**第一段 — クラウド (粗いフィルタ)**

クラウド側に「**研究プロフィール**」という軽量なテキスト資産のみを置く。具体的には以下。

- 研究テーマを表すキーワード群
- 自分の研究の概要文（自分で書いた、公開しても差し支えない数百字程度の要約）
- 既読・既知論文の DOI / arXiv ID のリスト（識別子のみ。本文やメモは含まない）
- 追跡対象の著者リスト・会議/ジャーナルリスト

生の実験データ、実験ノート、書きかけの原稿はクラウドに置かない。プロフィールは「学会発表の概要程度には公開している情報」の範囲に留める。

cron はこのプロフィールを用いて、新着論文にキーワード一致・引用関係・著者一致等による関連度スコアを付け、閾値を超えた候補のみを日次レポートとして D1 に保存する。ここでの目的は**再現率を優先した絞り込み**であり、取りこぼしを避けるため閾値は緩めに設定する。

**第二段 — ローカル (精密フィルタ)**

デスクトップ起動時、D1 から取り込んだ候補に対してローカル RAG で精密な判定を行う。

- 自分の研究データとのベクトル類似検索による重複判定
- 書きかけの原稿との照合
- 「活用できそうか」の判定
- ここで**適合率を優先**し、実際にユーザーに提示するものを絞る

クラウドは広く浅く、ローカルは狭く深く。

## 検討した代替案

**全件を D1 に保存してローカルで全部判定する** — クラウド側にプロフィールを置く必要がなくなり、機密性の面では最も安全。しかし同期データ量が大きく、ローカルでの埋め込み推論も全件分必要になる。分野が広い場合に実用的でない。将来、対象分野が十分狭いと判明した場合は再検討の価値がある。

**プロフィールにも未公開情報を含めて精度を上げる** — ADR-0003 の原則に反する。却下。

## 帰結

**良い点**

- 未公開データをクラウドに出さずに、日次の自動絞り込みが成立する
- D1 に流れるデータ量が管理可能な規模に収まる
- 第一段の閾値を緩めておけるため、取りこぼしはローカル側で救える

**悪い点**

- 判定ロジックが2箇所に分散し、挙動の追跡が難しくなる
- 研究プロフィールの手動メンテナンスが必要。研究の方向が変わったときに更新しないと、第一段の精度が落ちて静かに劣化する
- 第一段で落とした論文はローカルから見えない。閾値設定を誤ると取りこぼしに気付けない

## 緩和策

- 第一段のスコアと判定理由をレポートに含め、なぜ選ばれた／落とされたかを後から検証できるようにする
- 閾値未満の論文も識別子とスコアのみは D1 に残し、「今日は何件を閾値で落としたか」を可視化する
- 研究プロフィールの更新をアプリ側から促す（一定期間未更新なら通知する）
