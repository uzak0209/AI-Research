# ADR-0009: 分野固有の知識をコードに埋め込まず、設定とアダプタに外出しする

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

初期の ADR 群は暗黙に「自分の 1 つの研究テーマ」を前提にしていた。
README の未決事項に「論文ソースと埋め込みモデルは対象研究分野に依存するため、
分野確定後に決定する」と書いてあるのがその現れである。

しかし本ツールの目標は **どの分野のどの論文を書くときにも使えること**であり、
配布も前提にする（ADR-0008）。分野が決まらないと設計が決まらない構造それ自体が、
目標に対する欠陥である。

分野依存が漏れている箇所は 2 つに特定できた。

1. **ADR-0006 が specter2 と Semantic Scholar に強く結合している。**
   specter2 は英語論文のタイトル+要約で学習されており、人文系や
   国内ジャーナル中心の分野では収録率と精度が落ちる
2. **論文ソースが単一前提**。分野ごとに一次情報源が違う
   （CS なら arXiv、生医学なら PubMed、全分野なら OpenAlex）

一方、ADR-0002（クラウド/ローカル分離）、ADR-0003（ローカル完結 RAG）、
ADR-0004（二段フィルタ）、ADR-0005（Electron + TS）は分野に依存していない。
これらは変更不要である。

## 決定

分野固有の知識を **コードに置かず、アダプタと設定に外出しする。**

### 1. 論文ソースをアダプタ化する

`PaperSource` インターフェースを定義し、各ソースを差し替え可能な実装にする。
有効化するソースは設定で選ぶ。分野が変わればソースを足すだけで、コアは触らない。

```ts
interface PaperSource {
  id: string;                    // "arxiv" | "semantic-scholar" | "openalex" | ...
  fetchRecent(since: Date, profile: ResearchProfile): Promise<PaperMeta[]>;
  capabilities: {
    fullText: boolean;           // 全文 PDF が取れるか
    citations: boolean;          // 引用ネットワークが取れるか
    embedding?: EmbeddingSpec;   // ソースが埋め込みを配布しているか
  };
}
```

`capabilities` が要点である。「arXiv は全文 PDF があるが埋め込みは無い」
「Semantic Scholar は specter2 を配布する」といった差を、
**コアが個々のソースを知らずに扱える**。

### 2. 研究プロフィールをスキーマ化する

ADR-0004 の「研究プロフィール」を構造化データとして定義する。
分野固有の知識はすべてここに集約し、コードには一切置かない。

- キーワード群 / 追跡する著者 / 追跡する会議・ジャーナル / 除外条件
- 自分で書いた公開可能な研究概要

### 3. プロジェクト単位で分離する

「どの論文を書くときにも」の核心。現行 ADR は暗黙に「研究は 1 つ」を前提にしている。
**プロジェクト（論文）単位**でプロファイル・RAG インデックス・レポート履歴を分ける。

- テーマを移っても過去の資産が残る
- 複数の論文を並行して進められる
- ベクトル空間は **プロジェクト × 用途** の 2 次元になる（ADR-0006 を ADR-0012 で置き換え）

### 4. スキーマに user 次元を持たせる

配布（ADR-0008）を前提とするため、D1 のスキーマとストレージの分割に
最初から `user_id` を含める。**実装をマルチユーザー化するかは別問題**だが、
後からスキーマに次元を足すのは移行が高コストなので、今から入れておく。

### 禁止事項

- 特定の分野名・会議名・モデル名を**コードに定数として書かない**。設定に置く
- 特定ソースの API レスポンス形状をコアのデータ構造にしない。アダプタで正規化する
- 「デフォルトは CS 分野」のような暗黙の前提を置かない

## 検討した代替案

**分野ごとにフォークする** — 単純だが、本体の改善が各フォークに伝播しない。却下。

**すべてのソースを常に有効にする** — 設定が不要になるが、不要な API を叩き、
分野外の論文でノイズが増える。ソースごとのレート制限も無駄に消費する。却下。

**プロジェクト分離を後回しにする** — 初期実装は軽くなるが、
RAG インデックスとレポート履歴に後からプロジェクト次元を足すのは
データ移行が必要になる。ADR-0003 のローカル DB も作り直しになる。却下。

## 帰結

**良い点**

- 分野が未確定でも設計と実装を進められる。「分野確定待ち」の依存が消える
- 分野を移る・複数論文を並行する場合に、過去の資産が使える
- 新しい論文ソースの追加がアダプタ 1 つの追加で済む
- 配布時に、利用者が自分の分野に合わせて設定できる

**悪い点**

- 抽象化のコストがかかる。単一分野に決め打ちするより初期実装が重い
- `capabilities` の設計を誤ると、アダプタを追加するたびにコアの変更が必要になる
- プロジェクト × 用途の 2 次元インデックスは管理が複雑になる
- 設定項目が増え、オンボーディングの難度が上がる。初期プリセットの用意が必要
