# ADR-0014: Zotero 連携はローカル API を主、Web API を副とする

- **ステータス**: 承認済み（§3「OAuth は採らない」は **ADR-0015 により置き換え済み**）
- **日付**: 2026-09-19

## コンテキスト

ゴール成功条件 3: 関連論文を Zotero に保存できる。対象ユーザーは **Zotero 利用が前提**（`FR-05`）。
保存はデスクトップ責務（ADR-0002）。経路候補はローカル API と Web API。

| | ローカル API | Web API (`api.zotero.org`) |
|---|---|---|
| 到達先 | `http://127.0.0.1:23119/api/` | クラウド上のユーザライブラリ |
| 前提 | Zotero デスクトップが起動し、設定で他アプリ通信を許可 | ネット接続。アプリ起動は不要 |
| 認証 | 読み取りは無認証。書き込みはローカル確認ダイアログ（Zotero 10+） | 利用者の API キー、または OAuth 1.0a で取得した長期キー |
| オフライン | 可 | 不可 |

※ 初期メモにあった「7000 番」は誤り。公式のローカル API は **23119** である。

Web API の認証について整理する。**毎回のログインは不要**である。
必要なのは利用者ライブラリに紐づく長期 API キーであり、取得経路は次のいずれか。

1. **手動キー** — 利用者が zotero.org の設定画面で一度キーを発行し、アプリに貼る
2. **OAuth 1.0a** — ブラウザで一度許可し、アプリが長期キーを受け取る

OAuth にはアプリ登録で得た Client Key / Client Secret が要る。
これを Electron に同梱すると ADR-0008 の Orca キーと同型に見えたが、**性質は違う**。

| | OrcaRouter API キー (ADR-0008) | Zotero OAuth Client Secret |
|---|---|---|
| 漏洩時 | 開発者課金の暴走、全利用者の LLM 呼び出しに使える | **他人のライブラリには入れない**。利用者の許可なしに読み書きできない |
| 実際のリスク | 課金・悪用が直結 | 偽クライアントが「当アプリ」名義で OAuth を行い、利用者が誤って許可する余地（アプリなりすまし） |
| 対策の必然性 | **必須**（BFF / Workers Secrets） | 望ましいが、課金リスクほどの絶対要件ではない |

つまり OAuth Client Secret の同梱は「悪いが ADR-0008 級ではない」。
BFF に寄せれば Secret は守れるが、参考文献保存のためだけに Zotero 経路を
SaaS 化するコストに見合わない。

## 決定

**ローカル API を主経路、Web API（手動キー）を副経路とする。**
OAuth は初期実装に含めない。

### 1. 主: ローカル API (`127.0.0.1:23119`)

- エンドポイントは Web API v3 互換のローカル実装（`/api/` 配下）
- 設定で「Allow other applications on this computer to communicate with Zotero」が必要
- アプリ側に zotero.org の秘密は持たない
- 書き込み先はローカル DB。クラウド同期は利用者が Zotero 側で行う
- Zotero 未起動・ローカル API 無効時は失敗を隠さず提示し、副経路または再試行を案内する（ADR-0011）

### 2. 副: Web API + 利用者が発行した API キー

- Zotero を常時起動したくない利用者向け
- キーと `userID` は OS の secure storage に保存する（ADR-0008 のトークン保管方針と同じ）
- **開発者の共有キーは使わない。** 利用者本人のライブラリ資格情報のみ
- BFF を経由しない。保存メタデータ（タイトル・DOI 等）を自サーバに通さない

### 3. OAuth は採らない（初期） — **置き換え済み (ADR-0015)**

> 本節は ADR-0015 により無効。Web API 資格情報は OAuth 1.0a（BFF が Secret を保持）で取得し、
> 手動キーは退避とする。主経路がローカル API である点は変わらない。

- 手動キーで副経路の要件は足りる
- Client Secret の置き場（Electron vs BFF）の設計負債を初期に抱えない
- 将来ワンクリック接続が必要になったら、別 ADR で BFF 経由 OAuth を起案する

### データ分類（ADR-0010）

Zotero へ送るのは公開論文の書誌情報（タイトル、著者、DOI、URL 等）が主である。
未公開原稿本文は送らない。分類は **C1 相当の外部書き込み**だが、
経路は OrcaRouter / BFF ではなく Zotero（ローカルまたは利用者アカウント）である。
エンドポイントを LLM 系と相乗りさせない。

## 検討した代替案

**Web API + OAuth を主にする** — UX は良い。Client Secret を Electron に置くリスクは
ADR-0008 級ではない（上記表）。しかし Zotero アプリ利用者にはローカル API で足り、
OAuth アプリ登録とコールバック実装が先行する。初期は過剰。却下。

**Web API + OAuth を BFF 経由にする** — Secret は守れる。一方で参考文献保存が
自サーバ依存になり、障害面と運用面が増える。Orca キー保護ほど必然性が無い。却下（将来可）。

**Web API + 手動キーのみ** — 実装は単純。しかし本ツールの想定利用者は
Zotero デスクトップを日常的に使う層であり、起動中ならローカルの方が速く・オフライン可。
主経路にはしない。

**Connector プロトコルのみ（古い書き込み経路）** — Zotero 7 系ではローカル
`/api/` の書き込みが限定的だった経緯がある。現行はローカル API の書き込み認可
（Zotero 10+）を前提にし、必要なら Connector を実装詳細で補う。決定の軸にはしない。

## 帰結

**良い点**

- アプリに Zotero / Orca いずれの共有秘密も埋め込まない
- オフラインでもローカルライブラリへ保存できる
- ADR-0002（デスクトップ責務）・ADR-0008（キーをクライアントに置かない）・
  ADR-0011（不通時はキュー）と整合する
- Overleaf を「同期フォルダのローカル監視」にした ADR-0013 と同型
  （専用クラウド橋を作らず、既存ローカル状態を見る）

**悪い点**

- 主経路は Zotero デスクトップ起動が前提。未起動時は副経路か待機が必要
- 手動キーの副経路は初回セットアップの摩擦がある
- ローカル API の書き込み認可の詳細は Zotero のバージョンに依存する。
  `research-trend` スキャンの監視対象に含める
