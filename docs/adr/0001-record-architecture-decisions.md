# ADR-0001: アーキテクチャ決定を ADR として記録する

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

本プロジェクトは「毎日自動で最新論文を収集・解析し、自分の研究との重複や活用可能性を報告し、Zotero に参考文献を保存する」システムである。

設計上、以下のような判断が積み重なる。

- クラウドとローカルのどちらで処理するか（データの機密性に直結する）
- 未公開の研究データを外部 API に送信してよいか
- ベクトル空間をどう分離するか

これらは一度決めると後から覆すコストが高く、かつ「なぜそう決めたか」が失われると数ヶ月後の自分が同じ議論を繰り返す。特に本プロジェクトは個人研究の未公開データを扱うため、プライバシー上の判断根拠を残すことに意味がある。

## 決定

アーキテクチャ上の重要な決定を、Michael Nygard 形式の ADR として `docs/adr/` に記録する。

- ファイル名は `NNNN-kebab-case-title.md`
- 一決定ごとに一ファイル
- ステータスは `提案中` / `承認済み` / `却下` / `非推奨` / `置き換え済み`
- 決定を覆す場合は既存 ADR を書き換えず、新しい ADR を起こして旧 ADR のステータスを `置き換え済み (ADR-XXXX による)` に変更する

## 帰結

**良い点**

- 決定の理由が残るため、再検討のコストが下がる
- 「未公開データを外部に出さない」といった原則が明文化され、実装時のブレを防げる

**悪い点**

- ADR の維持に手間がかかる。決定と実装が乖離すると、かえって誤解を生む
