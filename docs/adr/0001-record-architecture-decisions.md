# ADR-0001: アーキテクチャ決定を ADR として記録する

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

プロダクトの目標・成功条件は [docs/requirements/00-goals.md](../requirements/00-goals.md) を正とする。
要約すると次を一つの流れで支援するシステムである。

- 日次の公開論文追跡（起動不要）
- 自分の研究との重複・活用可能性の報告
- 次のテーマ候補の提示
- Zotero への参考文献保存
- 執筆中原稿のファクトチェック
- 外部 LLM の統制された利用（これ自体が目的に含まれる）

設計判断（クラウドとローカルの分担、未公開データの扱い、ゲートウェイ選定など）は
覆すコストが高く、「なぜそう決めたか」が失われると議論が繰り返される。
未公開データを扱うため、判断根拠を残す意味が大きい。

**何を作るかは要件、どう作るかは ADR。** 混同しない。

## 決定

アーキテクチャ上の重要な決定を、Michael Nygard 形式の ADR として `docs/adr/` に記録する。

- ファイル名は `NNNN-kebab-case-title.md`
- 一決定ごとに一ファイル
- ステータスは `提案中` / `承認済み` / `却下` / `非推奨` / `置き換え済み`
- 決定を覆す場合は既存 ADR を書き換えず、新しい ADR を起こして旧 ADR のステータスを `置き換え済み (ADR-XXXX による)` に変更する
- 新しい ADR には、満たすゴール／要件 ID（`FR` / `C` / `NFR`）をコンテキストに書く

## 帰結

**良い点**

- ゴールと手段の対応が辿れる
- プライバシー・配布・外部 LLM に関する判断根拠が残る

**悪い点**

- ADR の維持に手間がかかる。要件と乖離すると誤解を生む
