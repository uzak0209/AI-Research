# ADR-0010: LLM に送るデータを分類し、分類ごとに経路と統制を変える

- **ステータス**: 承認済み
- **日付**: 2026-09-19

## コンテキスト

ADR-0007 で LLM 呼び出しを OrcaRouter に統一し、ADR-0008 で BFF を挟むと決めた。
ここで ADR-0003（未公開データの恒久インデックスを外部に作らない）との整合が問われる。

ファクトチェック機能は**執筆中の原稿本文をプロンプトに載せる**。
これは未公開の研究成果そのものである。

### 調査で判明した重要な事実（2026-09-19 時点）

OrcaRouter のゼロデータ保持について、ドキュメントは次を明言している。

> 「プロンプトと出力はメモリ上で処理され、ディスクに書かれることはない」
> — 既定で有効。ヘッダやパラメータ、プラン条件は不要

しかし同じページに決定的な限定がある。

> 「この保証は OrcaRouter のサーバのみを対象とする。OrcaRouter は選択された
> 上流（OpenAI、Anthropic、Google など）へトラフィックを転送し、
> **それぞれのプロバイダ自身の規約と保持ポリシーの下に置かれる**」
> 「OpenAI は 30 日の不正利用ログを保持する。Anthropic も同様」

**つまり「BFF → ゲートウェイ → プロバイダ」という経路にしても、
未公開の原稿が外部に残らないわけではない。** ゲートウェイ自身は残さないが、
上流プロバイダは自身のポリシーで保持する。

さらに ADR-0007 の通り、アダプティブルーティングは上流を動的に選ぶ。
**放置すれば、原稿がどのプロバイダに渡るか予測できない。**
チャネル固定（`channels:` / `@channel:`）は現時点で未提供のため、
物理経路まで固定することもできない。

この状態を「ゲートウェイがゼロ保持だから安全」と説明するのは誤りであり、
セキュリティ上の主張として成立しない。

## 決定

**データを 3 分類し、分類ごとに経路・許可モデル・同意要件を変える。**
分類はサーバ側（BFF）が機能ごとに決定する。クライアントの申告を信用しない。

### 分類

| 分類 | 内容 | 該当機能 |
|---|---|---|
| **C1 公開** | 公開済み論文のメタデータ・要約、公開情報のみ | トレンド解析、論文要約 |
| **C2 準機密** | 自分で書いた公開可能な研究概要・キーワード（ADR-0004 の研究プロフィール） | 新着論文との関連度・重複判定 |
| **C3 機密** | 未公開の原稿本文、実験ノート、実験データ | ファクトチェック |

### 分類ごとの統制

| | C1 公開 | C2 準機密 | C3 機密 |
|---|---|---|---|
| 経路 | BFF → OrcaRouter | BFF → OrcaRouter | BFF → OrcaRouter |
| 使用キー | `cron` | `interactive` | `sensitive` |
| モデル選択 | 自動選択・フォールバック可（コスト最適化） | 許可リスト内 | **単一モデルに固定**（`use: { model: ... }`） |
| プロバイダ | 制限しない | 許可リスト | **ZDR 相当の条項を確認済みのプロバイダのみ** |
| 自動フォールバック | 有効 | 有効（許可リスト内） | **無効。**失敗時は代替プロバイダに流さずエラーを返す |
| ガードレール | PII Shield（既定） | PII Shield | PII Shield + 出力段チェック、`fail_open: false` |
| ユーザー同意 | 不要 | 初回のみ | **機能の初回実行時に明示的な同意。**送信範囲を提示 |
| 送信範囲 | 制限なし | プロフィールのみ | **必要な範囲のみ。**ただし機能により適用可否が異なる（後述・ADR-0013） |
| 監査ログ | 機能・コスト | 機能・コスト | 機能・コスト・**送信範囲の要約**（本文は残さない） |

### C3 に対する追加の統制

**1. 自動フォールバックを無効にする**

C3 で最も危険なのは、障害時に想定外のプロバイダへ原稿が転送されることである。
ADR-0007 のフェイルオーバーは C1/C2 では利点だが、**C3 では脆弱性になる**。
C3 は単一モデルに固定し、失敗したら素直にエラーを返す。
可用性より秘匿性を優先する。

**2. 送信範囲を最小化する（機能によって適用可否が異なる）**

原則として、その処理に必要な範囲のみを送る。
関連論文の引き当てはローカル RAG（ADR-0003, ADR-0012）で行い、
外部に問い合わせない。

ただし **LLM による主張文抽出を行う機能では、この統制は原理的に適用できない。**
抽出前は原稿のどこが主張文か不明なため、セクション単位以上の
まとまったテキストを送る必要がある。

ファクトチェック機能は ADR-0013 でこの構成を採用した。
**その代わりに、経路の統制（モデル固定・フォールバック無効・ガードレール）と
透明性（送信内容のプレビュー、正確な同意文言）を厚くする。**
詳細は ADR-0013。

パース段階でコメント・数式環境を機械的に除外することは、
トークン削減と精度向上を主目的としつつ、副次的に送信内容を減らす。

> **注意**: 送信範囲を最小化できない機能では、同意画面で
> 「主張文のみ送信される」と誤認させる表現を使ってはいけない。
> 実際に送る範囲を正確に提示する。

**3. 明示的な同意と可視化**

C3 の機能を初めて使うとき、**何が外部に送られるかを具体的に提示**して同意を取る。
「外部 LLM に送信されます」という抽象的な文言では不十分。
実際に送信するテキストをプレビューできるようにする。

また、上流プロバイダが保持ポリシーを持つこと（OpenAI/Anthropic の
30 日不正利用ログ等）をこの画面で明示する。ゲートウェイのゼロ保持を
根拠に「残りません」と説明してはいけない。

**4. C3 を完全に無効化できる設定を用意する**

機関の規定（IRB、共同研究契約、企業との NDA）により、
未公開データを外部 LLM に送れない利用者が現実に存在する。
**C3 機能を設定で完全に無効化でき、無効時も他の機能が動く**ようにする。

将来的にローカル LLM による C3 処理を選択肢として追加する
（ADR として別途起案）。本 ADR ではその余地を残すに留める。

### 分類の判定はサーバ側で行う

クライアントが「これは C1 です」と申告する形にしてはいけない。
改造したクライアントが C3 データを C1 経路で送れてしまう。

ADR-0008 の通り**機能ごとにエンドポイントを分け、
エンドポイントが分類を決める**。ファクトチェックのエンドポイントは
常に C3 の統制を適用する。

## 検討した代替案

**すべて C3 相当の最も厳しい統制で扱う** — 安全側に倒れるが、
トレンド解析で自動ルーティングによるコスト最適化が使えず、
フォールバックも効かないため可用性も落ちる。公開論文にその保護は不要。却下。

**分類せず全て外部に送る** — 実装は最も単純。しかし ADR-0003 の原則と
矛盾したまま放置することになり、「未公開データをどう扱うか」への回答が無い状態になる。
配布して他人の研究データを扱う立場では成立しない。却下。

**C3 をローカル LLM のみで処理する** — 最も安全。しかしローカル LLM の
導入（モデル配布、推論環境、品質担保）が必須になり、実装量が大きく増える。
今回は「C3 を無効化できる」ことで代替し、将来の選択肢として残す。

**ゲートウェイのゼロ保持を根拠に C3 を無条件に許可する** — 調査の通り
上流プロバイダには適用されないため、事実に反する。却下。

## 帰結

**良い点**

- ADR-0003 との関係が明確になる。「埋め込みは出さない、プロンプトは統制下で出す」
  という非対称性に根拠がある
- C1 ではコスト最適化を、C3 では秘匿性を、それぞれ適切に優先できる
- 機関規定により外部送信できない利用者も、C3 を切って他機能を使える
- 何が外部に出るかをユーザーが判断できる

**悪い点**

- 分類ごとに経路と設定が分岐し、実装とテストが複雑になる
- C3 でフォールバックを切るため、その機能の可用性は上流プロバイダに直接依存する
- 送信範囲の最小化のため、ファクトチェックの前処理（主張文抽出）を自前で実装する必要がある
- 同意フローが増え、初回体験の摩擦になる
- 分類の線引きを誤ると、C3 相当のデータが C2 経路を通る。
  機能追加時は必ず分類を判定する手順が必要

## 運用上の注意

- **新しい機能を追加するときは、必ずデータ分類を決めてからエンドポイントを作る。**
  既存エンドポイントに機能を相乗りさせると分類が崩れる
- OrcaRouter のガードレールは advanced rule（judge / external）が既定で
  fail-open であり、「一時的なエラー時は強制せず通す」挙動になる。
  C3 では `fail_open: false` を明示し、**検証できないなら通さない**
- 上流プロバイダの保持ポリシーは変わりうる。`research-trend` スキャン
  （ADR は `.github/claude-scans/research-trend.md`）の監視対象に含める
